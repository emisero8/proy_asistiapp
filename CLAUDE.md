# Guía de Desarrollo AsistíAPP (Full-Stack)

- **Qué es este archivo:** instrucciones y contexto para el asistente de código (Claude) que trabaja en este repo. Para una visión general del proyecto, ver `README.md` y `docs/README.md`.
- **Retomando el trabajo (sesión nueva o PC nueva): leer primero `docs/proyecto/CONTINUAR.md`** (dónde estamos, qué falta, trampas conocidas y cómo montar el entorno) y la sección "Estado actual" de `docs/proyecto/PLAN_MEJORAS.md`.
- **Repo:** monorepo en GitHub (`proy_asistiapp`), raíz en `AsistiApp/`. `backend/` (Java/Spring Boot) y `frontend/` (React/Vite) son hermanos en el mismo repo.
- **Frontend real:** `frontend/` — proyecto Vite + React + TypeScript, desarrollado y buildeado con `npm install && npm run dev` / `npm run build`. Estructura multi-archivo normal: `src/App.tsx` (router), `src/lib/` (api.ts, auth.tsx, types.ts, format.ts), `src/pages/{buyer,organizador,staff,admin}/`.
- **Stack Frontend:** React + TypeScript + Tailwind CSS v4, `react-router` (v7, paquete unificado, no hace falta `react-router-dom`), `recharts` para gráficos.
- **Stack Backend:** Java + Spring Boot + PostgreSQL.
- **Iconos (Frontend):** lucide-react v0.487.0 (IMPORTANTE: Usa `CircleX`, NUNCA `XCircle`).

## 🎨 SISTEMA DE DISEÑO (FRONTEND - CRÍTICO)
Para estructurar componentes, utilizar colores (`--primary`, `--card`, etc.), espaciados y tipografías, **DEBES leer y aplicar estrictamente las reglas del archivo `docs/tecnica/DESIGN.md`**. Si la tarea es rediseñar pantallas, leer también `frontend/GUIA_REDISENO.md`. 
- Usa la sección "Component Patterns" del `docs/tecnica/DESIGN.md` para crear botones, inputs y tarjetas. No inventes clases de Tailwind.

## ⚙️ ARQUITECTURA Y DATOS (BACKEND - CRÍTICO)
Para cualquier tarea relacionada con la base de datos, creación de endpoints, lógica de negocio o integraciones, **DEBES leer el archivo `docs/tecnica/API.md`** (modelo de datos, endpoints y reglas de negocio).
- **Seguridad:** Usa Spring Security con JWT Stateless. Verifica siempre los roles del sistema (`Administrador`, `Organizador`, `Staff_QR`, `Staff_Vendedor`).
- **Reglas de Negocio:** Respeta estrictamente los casos de uso definidos (ej. publicar un evento consume créditos, la validación de QR marca la entrada como usada).
- **Transacciones (ACID):** Usa `@Transactional` en los servicios que modifican datos para evitar sobreventa de entradas (controlando rigurosamente el `cupo_disponible` en la entidad `TANDA`).
- **Patrones de Código:** Usa siempre DTOs para las peticiones/respuestas (no expongas entidades JPA) e implementa manejo de errores global estructurado con `@ControllerAdvice`.
- **Contrato con el frontend:** si cambiás un endpoint o un DTO, `OpenApiContratoTest` falla hasta que se regenere la copia del contrato del frontend: con el backend corriendo, `cd frontend && npm run types:api`, luego `npx tsc -b` y actualizar `frontend/src/lib/types.ts` donde marque (detalle en `frontend/README.md`, "Contrato con el backend").

## 💳 COBRO CON MERCADO PAGO / ETAPA 8 (CRÍTICO)
Para cualquier tarea que toque pagos, reembolsos, la cuenta de Mercado Pago del Organizador, entradas anuladas o el cobro de créditos, **DEBES leer `docs/tecnica/MERCADOPAGO_COBRO.md`** (modelo, mapa del código, flujos, cómo preparar el entorno, cómo probar, hallazgos del sandbox y trampas). La especificación está en `docs/proyecto/MODELO_DE_COBRO.md` y el estado en `docs/proyecto/PLAN_MEJORAS.md` (Etapa 8).
- **Las entradas se cobran con el token OAuth del Organizador del evento; los créditos, con el de la plataforma.** Cada llamada a Mercado Pago lleva su propio token (`MPRequestOptions`): nunca cambies el token global del SDK. Las llamadas a Mercado Pago van **fuera** de las transacciones de base.
- **Con la cuenta de un Organizador se usa `init_point`**, no `sandbox_init_point`.
- **El cobro con OAuth no se puede probar con usuarios de prueba del sandbox** (investigación abierta en la guía, sección 7). Se prueba con `MP_EXIGIR_CUENTA_VINCULADA=false` (cobra con la cuenta de la plataforma) o con dinero real y montos mínimos.
- **No leas ni uses tokens de Mercado Pago guardados en la base** (descifrarlos y llamar a la API) sin autorización expresa de la persona, y nunca imprimas un token. Las credenciales van en variables de entorno o `backend/.env`, jamás en el repo, en los `.md` ni en el chat.
- Un valor nuevo de enum o una restricción nueva en Postgres necesita un script en `backend/db/migraciones/` (ver su `README.md`; `ddl-auto: update` no actualiza los CHECK). Para una base existente: `backend/db/aplicar-migraciones.ps1`.
- **Antes de pagar algo real con la persona**, avisar el monto y que Mercado Pago cobra comisión aunque se reembolse; pagar solo desde una cuenta distinta del vendedor.

## 🔌 INTEGRACIONES EXTERNAS — ESTADO ACTUAL (a propósito, no son bugs)
- **MercadoPago (Checkout Pro):** el **backend ya está integrado de verdad** (Fase 21 de `docs/tecnica/backend_implementation_plan.md`): preferencia real con `cantidad`, webhook con firma + verificación contra la API de MP, idempotencia, reembolso automático y mail desde el backend. **El frontend también está integrado** (Fase 12 de `docs/tecnica/frontend_implementation_plan.md`): `CheckoutPage` y `WalletPage` redirigen al checkout real y `PagoResultadoPage` espera la confirmación. El contrato cambió respecto de la versión simulada: `ordenId` es un UUID string, `urlPago` es el `init_point` real, `comprar-online` recibe `cantidad` y ya no existen `/tickets/webhook/pago` ni `/creditos/webhook/pago`.
  - **Credenciales por variable de entorno (o `backend/.env`), nunca en el repo, en los .md ni pegadas en el chat:** `MP_ACCESS_TOKEN`, `MP_WEBHOOK_SECRET` y `MP_WEBHOOK_SECRET_PRODUCCION` (una por modo del panel), `BACKEND_PUBLIC_URL`, `MP_VALIDAR_FIRMA` (ver tabla en la Fase 21). En esta máquina están guardadas como variables de entorno del usuario de Windows (hay que reabrir la terminal/VS Code para que las tomen).
  - **`MP_VALIDAR_FIRMA=false` es solo para el sandbox local** (los avisos de pagos reales de prueba llegan firmados con una clave que no coincide con la del panel — ver "Pendiente de la firma" en la Fase 21). **En producción debe ser `true`.**
  - **Completar un pago en local NO necesita túnel público:** si el webhook no llega, la orden se confirma igual por reconciliación — `GET /tickets/orden/{ref}` (que consulta `PagoResultadoPage`) y el job de vencimiento buscan el pago en la API de MP (Fase 21.6; verificado en vivo con el túnel apagado). El túnel solo hace falta para **probar el webhook en sí**: `ngrok http --url=<dominio-estatico>.ngrok-free.dev 8080`, `BACKEND_PUBLIC_URL` con esa URL HTTPS (si no es HTTPS el backend lo avisa en el log y no manda `notification_url`) y el webhook cargado en el panel de MP (`<url>/payments/mercadopago/webhook`, evento "Pagos"). Comprador de prueba en incógnito.
  - **El pago como invitado (tipeando cualquier tarjeta de prueba, titular `APRO`) no funciona con credenciales de usuario de prueba** — MercadoPago lo rechaza con una pantalla de error genérica (`/fatal/`), tanto en automatización (Playwright) como en un Chrome real. Hay que loguearse con un **test user comprador** (botón "Ingresar con mi cuenta" en el checkout de MP) y pagar con "Dinero disponible" de esa cuenta. Los test users (comprador y vendedor) se crean/consultan desde el panel de developers de MP.
  - **No hay botón "Volver al sitio" ni auto-redirect en local:** `MercadoPagoService.crearPreferencia()` manda siempre `back_urls`, pero el `auto_return` (y en la práctica el botón manual también) solo los activa MercadoPago si `FRONTEND_BASE_URL` es HTTPS pública. Con el frontend en `http://localhost:5173` la pantalla de "pago aprobado" de MercadoPago se queda sin ningún botón de vuelta. **No es un bug a arreglar** — en producción (dominio real HTTPS) funciona solo. Por eso, cuando el frontend corre en `http`, el checkout se abre en una **pestaña nueva** y la original queda esperando en `/pago/resultado` hasta que el pago se aprueba (`lib/pago.ts`, ver `docs/proyecto/DECISIONES.md` 2026-11-10); después de pagar hay que volver a esa pestaña. Si hiciera falta entrar a mano: `http://localhost:5173/pago/resultado?ref=<externalReference>&tipo=entradas|creditos` (el `externalReference` queda logueado en el backend como `Preferencia MP creada: ... externalReference=...` y `Compra iniciada: ... ref=...`).
  - **El plan free de ngrok no soporta 2 túneles simultáneos** (uno para el backend y otro para tunelear también el frontend y así tener HTTPS real en local): si se intenta, ambos terminan "compitiendo" por el mismo dominio público y solo uno queda realmente activo (verificar con `curl -I <url>` — si devuelve 403 de Spring Security es el backend, no el frontend). No vale la pena perseguirlo sin pasar a un plan pago de ngrok.
  - **Si hay que reiniciar el backend a mano durante una sesión con el túnel ya levantado, hacerlo desde PowerShell, no desde una shell de Bash que ya estaba abierta antes de setear las variables de entorno de MercadoPago** (`MP_ACCESS_TOKEN`, `MP_WEBHOOK_SECRET`, `BACKEND_PUBLIC_URL`) — una Bash preexistente no las ve (quedó con el entorno viejo) y el backend arranca con "El cobro con MercadoPago no está configurado". En PowerShell, leerlas con `[Environment]::GetEnvironmentVariable('X','User')` y asignarlas a `$env:X` antes de lanzar `mvn spring-boot:run`.
  - **Antes de correr `mvn test`, si aparecen errores raros de compilación/contexto, usar `mvn clean test`** (la extensión de Java de VS Code deja clases sin Lombok en `target/classes`).
- **SMTP (envío de mails):** `EmailService` funciona con cualquier proveedor SMTP estándar. Por defecto apunta a **MailHog** (SMTP local en `localhost:1025`, UI web en `http://localhost:8025`), que se levanta con `docker compose up -d` desde la raíz del repo o, si Docker no anda, con el ejecutable standalone `MailHog.exe`. El SMTP se configura por variables de entorno (`SMTP_HOST`, `SMTP_PORT`, `SMTP_AUTH`, `SMTP_STARTTLS`, `SMTP_USERNAME`, `SMTP_PASSWORD`) o en un `backend/.env` opcional (ver `backend/.env.example`): **con un `.env` de Gmail cargado, todo mail que mande la app sale de verdad**; para volver a MailHog hay que borrar o renombrar ese archivo. Si el servidor SMTP no está disponible, el flujo de negocio igual se completa (diseño intencional — el fallo de mail solo se loguea).
